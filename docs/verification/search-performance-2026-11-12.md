# Global Search performance verification — 12 November 2026

## Result and scope

The maintained-data gate passed all **192 timed API responses**: 13 criteria,
two signed-in identities and three submissions per criterion, including every
subsequent page. The maximum was **2.8381 seconds**. The slowest subsequent page
was **0.4149 seconds**. No average or discarded first request was used to pass.

This verifies Global Search on the fixture below. It does not establish latency
for every other search endpoint, arbitrary hardware, concurrent production
load, browser rendering or network transit. See the normative
[search performance contract](../search-performance.md).
The companion [optimization lessons](../postgresql-search-optimization-lessons.md)
preserve the unsuccessful approaches and explain why the final design differs.

## Fixture and method

- 51,003 aggregations, 153,009 records, 153,009 components and 306,018 chunks.
- Simple, English and Arabic text configurations; repeated terms create score
  tiers and ties. Every record has two chunks.
- One ordinary role with explicit ACL grants and one with the same global
  privileges/clearance but no resource grants.
- A 1,000-result cap, 100 results per page and a strict three-second maximum
  for each response.
- PostgreSQL 18.4 on macOS 15.6.1 arm64, eight logical CPUs, `work_mem=4MB`.
  Data checksums and full-page writes remained enabled.
- Canonical schema/reference initialization, deterministic bulk loading, then
  normal `VACUUM ANALYZE`, following the existing dashboard benchmark setup.
- The broad combined query was the first measured request. No search or oracle
  calculation warmed the corpus before it. No first response was discarded.
- Timings cover the actual FastAPI request pipeline, including authentication,
  SQL, cache persistence, page attribution and serialization through TestClient.

The independent SQL oracle checks the exact uncapped matching count, top 1,000
IDs and scores, deterministic score/type/ID ordering, saved ranking, truncation
and complete page sequence. Every denied-access request returned zero hits.

## Query changes verified

The query now exposes fixed-configuration predicates to the existing full-text
GIN indexes and shares one scan branch across common language configurations.
The gate asserts GIN paths for selective metadata, content and filename cases.
Migration 109 adds the missing filename GIN index and small partial indexes for
fallback text configurations.

Roles, clearance and ACL decisions are shared across candidates. Compact
permission sets and explicit hierarchy uniqueness avoid misleading row-count
estimates. Parsed queries are reused for scoring. Match flags travel with
candidate IDs, and full text vectors are reduced to scores before later joins.
Chunk retrieval chooses indexed or bulk access from the actual permitted set;
it never truncates candidates to achieve the timer. Matching, authorization,
scoring, ranking and the cap remain in PostgreSQL.

The broader regression run passed 59 tests covering search, canonical permission
equivalence, retained resources, dashboards and the index upgrade. The final
search/permission subset passed 19 tests after the final SQL changes. It includes
the case where a metadata hit receives a positive component score even though
that chunk fails a negated query, preserving the existing ranking formula.

## First scan immediately after an unmaintained bulk load

The separately retained diagnostic failed the same latency limit: its first
full API request took **8.6123 seconds**, followed by about 2.40 seconds on
repeats. A fresh SQL profile identified **46,505 full-page WAL images**, totaling
**344,428,849 bytes**, generated by the first scan of freshly inserted chunks.
That chunk scan alone took 4.379 seconds; the record-ranking statement took
6.440 seconds. The chunk table had not yet been vacuumed.

These measurements are consistent with visibility-hint updates on freshly
committed rows. With checksums enabled, PostgreSQL
[logs those hint-bit page updates](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-WAL-LOG-HINTS).
Completing post-load vacuum maintenance moves this initialization work out of
the first user search. No durability settings were disabled.

The passing gate therefore describes a maintained database after bulk-load
setup. **It is not proof of a three-second bound immediately after an arbitrary
unvacuumed bulk import or on a cold disk.** Operations guidance records this
distinction; vacuuming is never placed in the search request path.

## Browser versus application latency follow-up — 12 November 2026

The earlier WebUI numbers above timed automation commands. They did not record
native click timestamps, so their exact automation overhead cannot be recovered
retroactively. Use the following paired measurements when discussing application
latency; do not treat the earlier roughly one-second totals as SQL/API times.

Temporary probes captured the native browser click, arrival of the new ten-row
DOM, and two animation frames. Separate server probes measured WebUI preparation,
HTTP requests, search stages, SQL statement counts and result construction.
Five fresh submissions and Next actions were measured per query, with the same
signed-in user, ten-row pages and 296/1,000-capped result totals. All twenty final
samples are retained. Times below are medians in milliseconds; stage medians

Browser ranges were 209.5–450.6 ms / 139.2–173.4 ms for `demo` first/Next,
and 596.4–719.2 ms / 245.2–373.3 ms for broad first/Next. Extra automation
time ranged from 48.8 to 286.8 ms in this run. The remaining browser/server
delivery and frame interval was approximately 33–54 ms. These are local
observations, not a concurrent-production latency guarantee.

Every measured Next entered `_read_global_search` and none entered
`_rank_global_search`. `_global_current_rows` checks the page plus its lookahead
candidate, re-evaluating current access, matching and scores for those IDs.
The full ranked corpus is not searched again. The search request nevertheless
executes 29 SQL statements on `demo` page 2 and 34 on broad page 2, including
per-result attribution/snippet work.

The WebUI then calls the general capabilities endpoint once per returned
record: 3/0 calls on `demo` first/Next and 10/2 calls on broad first/Next.
Each capability request normally executed 30 SQL statements, checking numerous
editing and hold operations as well as the display capabilities. Broad Next
therefore added 60 statements after the 34-statement search request. Broad first
added approximately 300 after its 51-statement search request. The next targets
are batched page checks/enrichment and returning just the required expansion and
preview capabilities with the page, preserving canonical permission decisions.

### Measurement interference found and corrected

The initial temporary logger synchronously opened/appended a file at request
completion. Captured Python stacks showed this diagnostic I/O blocking the API
event loop in `pathlib.open`, creating capability-response spikes of around a
second despite fast SQL. Those runs are retained as contaminated diagnostic
evidence, not reported as normal application latency. The final twenty samples
use a background writer queue. No timing sample from that final run was removed.
The browser clock also excludes time spent by the automation tool finding,
dispatching and confirming controls.

### Separate reconnect lock problem

During simultaneous reconnects after diagnostic code reloads, PostgreSQL showed
authentication waiting on the login-session row while a completed search
transaction remained idle and uncommitted. Main-thread stack samples located
the wait in `audit_request_context` → `resolve_principal` → synchronous
`SELECT ... FOR UPDATE OF s`. The search-cache foreign key holds a conflicting
session-row lock until its transaction commits; blocking the API event loop
prevents pending request cleanup from progressing. The two waits were recovered
by cancelling only the identified diagnostic authentication reads. This is
separate from the ordinary Next timings above and remains an implementation
issue; moving blocking authentication/database work off the event loop needs
its own permission/session and concurrent-request regression coverage.
